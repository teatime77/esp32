# Python VMから呼ぶC数値カーネルの仕様と接続設計

概要・使い方・作業計画は[簡易版](numeric-kernel-overview.md)を参照する。この詳細版は、実装時に参照する制約と接続形式を含む。

設計版1。Pythonプログラム全体は現在のPython VMで実行し、`@kernel`で指定した1要素分の数値関数だけをCへ変換する。`launch()`は指定要素数の計算を一度のネイティブ呼出しで実行する。目的は、VMによる要素ごとの命令解釈を省いて数値ループを高速化することである。

カーネル機能は段階的に実装する。Python側の構文解析・型解析・診断と、数値用中間表現・共通C・登録マニフェストの生成は実装済み。実装の仕様は[parser.ts](../../../../uroa/diagram/ts/python/parser.ts)、[syntax.ts](../../../../uroa/diagram/ts/python/syntax.ts)、[kernel.ts](../../../../uroa/diagram/ts/python/kernel.ts)、[semantic.ts](../../../../uroa/diagram/ts/python/semantic.ts)、[kernel-ir.ts](../../../../uroa/diagram/ts/python/kernel-ir.ts)、[kernel-c.ts](../../../../uroa/diagram/ts/python/kernel-c.ts)のコメントを正本とする。実行接続は後続段階で追加するため、カーネルを含むプログラムのバイトコード生成は明示的に拒否する。現在のバイトコードはversion 7であり、後述するversion 8、命令、実行時の登録表は追加設計である。

## 1 対象環境とコンパイル方針

| 環境 | 通常処理 | 数値計算 |
|---|---|---|
| ESP32 | C++製Python VM | 生成Cをファームウェアへ組み込んで実行 |
| ブラウザ | EmscriptenでWasm化したPython VM | 生成Cをブラウザ内でWasm化して実行 |
| Colab | Linux向けPython VM | 生成Cの共有ライブラリーを読み込んで実行 |

配列の確保・形状管理・通常の要素操作は、既存のVMと自作NumPyが担当する。数値カーネルは渡された数値バッファーへ直接アクセスし、要素ごとにVM・自作NumPy・TypeScriptを呼ばない。本家NumPy・matplotlibとの連携、ESP32機械語の直接生成、Wasmバイナリーの直接生成は対象にしない。

ブラウザ用のCコンパイラーは[wcc](https://github.com/tyfkda/xcc)を採用し、生成したWasmを[Binaryenのブラウザ用ライブラリー](https://github.com/AssemblyScript/binaryen.js)で最適化する。軽量さと導入の簡単さを優先し、複数のCコンパイラーの性能比較や、比較用Clangのブラウザ組込みは行わない。

```text
Pythonソース
    ├─ 通常処理 → バイトコード → Python VM
    └─ @kernel関数 → 数値用の型付き表現 → 共通の生成C
                                               ├─ ESP32の通常ビルド
                                               ├─ ColabのCコンパイラー
                                               └─ ブラウザのwcc → Binaryen → Wasm
```

wccはCからWasmを生成するコンパイラー、Binaryenは生成済みWasmの最適化処理である。選定は完了し、wccはコミット`659a1773f20499864a8c3fdc7cd25cb506092bc1`、Binaryenは`132.0.0`に固定する。[選定記録](browser-c-compiler.md)に依存、ライセンス、Worker接続と最適化設定を定める。配布量、コンパイル時間、VMとの接続の成立は後続の導入時に確認するが、別コンパイラーの選定競争は行わない。

## 2 Python側の宣言と呼出し

### 2.1 型とカーネル宣言

`kernel`、`launch`、`InF32`、`OutF32`はコンパイラーが認識する組込み名とし、importは不要とする。`InF32`と`OutF32`は型注釈だけで使い、実行時の型オブジェクトは生成しない。

```python
import numpy as np

@kernel
def saxpy(i: int, a: float, x: InF32, y: InF32, out: OutF32) -> None:
    out[i] = a * x[i] + y[i]

x = np.zeros(1000, dtype=np.float32)
y = np.zeros(1000, dtype=np.float32)
out = np.zeros(1000, dtype=np.float32)

launch(saxpy, len(out), 2.0, x, y, out)
```

| 表記 | 意味 |
|---|---|
| `int` | 符号付き32bit整数 |
| `float` | 単精度浮動小数点数 |
| `InF32` | 読取り専用の、連続した1次元float32配列 |
| `OutF32` | 書込み専用の、連続した1次元float32配列 |
| `-> None` | スカラーの戻り値を持たず、出力配列へ結果を書き込む |

`@kernel`はモジュール直下の関数だけに付ける。引数・戻り値の型はすべて明示する。先頭引数は`int`の実行インデックスであり、呼出元から実際の値を渡さない。先頭引数名は任意だが、例では`i`を使う。実行インデックスへの再代入を禁止し、`out[i]`が常にその実行自身の要素を示すようにする。残りはスカラー、入力配列、出力配列を宣言順に並べる。配列を再代入したり、スカラー引数を配列型へ変更したりできない。

型注釈と`@kernel`の構文解析は実装済みで、構文木は注釈・デコレーターの名前と元位置を保持する。型注釈はこの設計で使う型と単純な関数宣言を対象とし、typing全般や任意のデコレーター評価は導入しない。

### 2.2 launchの契約

呼出し形式は`launch(カーネル名, n, 宣言の第2引数以降...)`とする。

- カーネル名はコンパイル時に直接解決する。関数を変数へ格納する、名前を文字列で渡す、実行時に関数を選ぶ機能は追加しない。
- `n`は`int32`の非負値とし、`0 <= i < n`の各実行を起動する。
- `n`と明示引数の式は、左から右へ一度だけ評価する。
- `n == 0`でも登録・型・配列形式・共有状態を確認するが、計算とブラウザの配列コピーは行わない。
- 配列長と`n`、カーネル内部の添字の関係はプログラム側が保証する。`n <= len(array)`などの境界検査は追加しない。
- 結果は`None`であり、完了後にVMは次のPython処理へ進む。
- 通常の関数としての直接呼出し、キーワード引数、既定引数、可変長引数は初期版では受け付けない。

入力配列同士の共有は許す。各出力配列はすべての入力配列およびほかの出力配列と異なる本体でなければならない。この条件はlaunchの入口で確認する。初期版はスライスや部分ビューを扱わないため、VMの配列本体の同一性で判定する。

各実行が書き込めるのは、各`OutF32`の実行インデックスの要素だけである。初期版の書込み先は構文上の`out[i]`に限定する。出力配列の読取り、別インデックスへの書込み、入力配列への書込みはコンパイル時エラーとする。要素間の実行順序へ依存しないことを契約とし、将来のGPU実行でも順序を保証しない。

条件分岐により書き込まれなかった出力要素は、呼出し前の値を保つ。`n`以降の要素も変更しない。これは有効な添字だけを使用した場合の契約であり、不正なアクセスの回復や検査は行わない。

## 3 数値カーネル内で扱う機能

| 種別 | 初期版の対応 |
|---|---|
| 値 | int32、float32、比較結果。配列は宣言済みバッファーだけ |
| 演算 | `+`、`-`、`*`、`/`、単項符号、比較、論理演算 |
| 制御 | ローカル変数、代入、if/elif/else、有限なfor/while、break/continue、値なしreturn |
| 配列 | 入力の1次元添字アクセス、出力の`out[i]`、`len(array)` |
| 組込み関数 | 数値の`abs`、2引数の`min`・`max`、int32からfloat32への`float`変換 |
| 補助関数 | モジュール直下の、型注釈付きの純粋なスカラー関数 |

整数同士の`+`、`-`、`*`はint32とし、float32を含む演算と`/`はfloat32とする。`/`のC生成では整数同士でも浮動小数点除算になるように変換する。Cの浮動小数点リテラルにはf接尾辞を付け、意図せずdouble演算へ昇格させない。比較結果は条件用のboolとし、`and`・`or`・`not`もboolに限定する。数値を返すPythonの一般的なand/orや、boolを数値配列へ格納する操作は初期版では扱わない。論理演算の短絡評価と引数の評価順序は生成時に保つ。初期版では`//`、`%`、`**`、浮動小数点数から整数への変換を扱わない。

forは整数の`range`に限定し、ステップは正の整数定数とする。whileはループ変数・上限・更新から有限性を解析できるものに限る。この制約は静的な対応範囲であり、実行中の反復回数制限や停止検査を追加する意味ではない。配列内容に終了条件を委ねる探索や、有限性を確認できないループは初期版では診断する。

補助関数の引数・戻り値はint32またはfloat32とする。呼出し先を静的に確定し、呼出し関係に循環がないことを確認してCへ生成する。カーネルや補助関数から通常のVM関数を呼び戻さない。変更可能な大域変数、クロージャー、一般オブジェクト、再帰、動的確保、shape変更、文字列、例外、機器操作、描画、RPC、sleepは扱わない。

対応外の処理を自動的にVM実行へ置き換えず、元のPythonソース位置を付けて診断する。sin・cos・sqrtなどの追加数学関数は、ブラウザを含むC実装方法を確定した単位で対応表へ追加する。現在VMが持つ数学APIの全件対応は初期カーネルの前提にしない。

## 4 fast mathとチェックなし実行

カーネルの数値プロファイル名を`unsafe-fast-v1`とする。

- 配列の添字範囲、負の添字補正、整数オーバーフロー、ゼロ除算、NaN・Infの検査を生成しない。
- スカラー引数、入力配列の要素、出力配列の要素に対する有限性検査も行わない。
- 出力後の走査・有限性確認・補正は行わない。CからVMへ戻る際に非有限値を理由としてカーネルを失敗扱いにしない。
- 負の添字は通常のVM NumPyのように補正しない。すべての添字は呼出元とカーネル自身が有効に保つ。
- 数値演算はfast mathを有効にしたC実装に従い、VM実行や環境間のbit単位の一致は要求しない。
- 符号付き整数の範囲外演算を、GPUと同じ折返し演算としては規定しない。不正な添字・整数ゼロ除算・変換などの結果や回復も保証しない。
- Wasm実行系が持つメモリー境界や整数除算などのトラップは、このソフトウェア検査省略とは別に残る。

ESP32とColabでは生成した`.c`をCとしてコンパイルし、カーネルのコンパイル単位だけに`-O3 -ffast-math`を適用する。VMや機器処理には適用しない。カーネルとVMをまたぐLTOを初期版では使わず、リンク時にもVM全体の浮動小数点設定を変更しない。

ブラウザではwccで生成した計算用Wasmに、Binaryenの最適化とfast mathを適用する。[Binaryenのfast math設定](https://github.com/WebAssembly/binaryen/blob/main/src/tools/optimization-options.h)はNaN・丸め・負のゼロなどの扱いを緩める設定であり、ネイティブCコンパイラーと同一の変換や結果を保証するものではない。VM用Wasmにはこの設定を適用しない。

現在のNumPy実装は、通常の書込みが有限値を保つ前提を持つ。カーネル実装時には「カーネルが書いた数値配列は非有限値を含み得る」という例外を、配列操作・VM・ネイティブ変換の仕様コメントへ反映する。配列のdtype・形状・配置の保証は維持する。カーネル終了後に通常のVM演算や機器APIへ値を渡した場合は、その処理が持つ既存の検査が適用され得る。

## 5 生成Cの関数形式

各カーネルに1要素分の内部関数と、要素ループを持つ公開ラッパーを生成する。公開名は`uroa_kernel_<id>_run`とする。配列引数はデータポインターとint32の要素数へ展開し、`len()`は要素数を参照する。

例えばsaxpyの公開関数は次の形になる。これは生成形式の例であり、現在のC++ソースへ追加する関数ではない。

```c
void uroa_kernel_1_run(
    int32_t n,
    float a,
    const float *x,
    int32_t x_length,
    const float *y,
    int32_t y_length,
    float *out,
    int32_t out_length) {
    for (int32_t i = 0; i < n; ++i) {
        out[i] = a * x[i] + y[i];
    }
}
```

配列のヘッダー、VMのValue、GCの本体ポインター、機器ハンドルを生成Cへ公開しない。生成CはGC・再入・Python呼戻しを行わない。要素ループと1要素分の関数は同一コンパイル単位に置き、インライン化できる形にする。C++ホストからの接続宣言にだけ`extern "C"`を用い、生成C自体はC++構文を使わない。

## 6 登録情報とバイトコードの接続

### 6.1 カーネル登録表と識別情報

機器APIの`NativeApi`とは別に、プログラムごとのカーネル登録表を設ける。launchから参照されるカーネルだけを対象とし、名前のUTF-8バイト列の昇順で1からの非0 uint16 IDを割り当てる。名前は診断用、IDは呼出し用とする。

各登録項目はID、名前、先頭の実行インデックスを除く引数の型列、引数数、生成したラッパーへの接続を持つ。型タグの論理表記は`i32`、`f32`、`in_f32`、`out_f32`とする。1つのPython実引数は1つのVM Valueであり、配列はVMの参照1個で渡す。Cのポインターと長さへの展開はホスト側のアダプターが担当する。

カーネル集合のSHA-256を`kernelSetHash`とする。ハッシュ入力は次の配列を、空白を挿入しないJSONとしてUTF-8化したものとする。

```text
[1, "unsafe-fast-v1", generatedC, [[id, name, [argumentType, ...]], ...]]
```

`generatedC`は要素関数・公開ラッパー・純粋なヘルパーを含む共通の生成Cで、改行をLFに統一する。環境別の登録アダプターやブラウザ用の割当て・export用接続コードは含めず、それぞれ成果物のビルド条件として管理する。絶対パス、時刻、通常のVM処理の行番号など、カーネルの意味に無関係な情報も含めない。文字列のエスケープはJSON.stringify相当とし、項目の順序は上記の配列順に固定する。引数の型列は実行インデックスとlaunchの要素数を除く宣言順とする。

カーネル一覧・型・生成C・プロファイルが変わればハッシュが変わる。通常のVM処理だけの変更では変えない。ソース位置は別のデバッグ情報に保持する。機器APIの既存ABIハッシュとは混ぜない。

成果物のマニフェストは設計版、プロファイル、kernelSetHash、各ID・名前・型列・公開名、コンパイラー／Binaryenの固定バージョンと設定を持つ。対象環境、ビルド設定、カーネルのハッシュをキャッシュキーに使い、実行前に登録表のハッシュを照合する。JSONマニフェストやCコードはESP32の通常のプログラム転送には含めない。

### 6.2 バイトコードversion 8

カーネル呼出しを含むプログラムには、以下のversion 8形式を追加する。カーネルを使わないプログラムは既存version 7を維持する。実装後の受信器・VM・デバッガーは両方を区別して扱う。

| 部分 | version 8の設計 |
|---|---|
| ヘッダー長 | 96バイト |
| offset 0〜63 | versionフィールドを8とし、それ以外の項目と意味はversion 7を維持 |
| offset 64〜95 | kernelSetHashの32バイト |
| offset 96以降 | version 7と同じ順序の関数表、型表、命令列、文字列表、UTF-8データ |
| カーネル命令 | `CALL_KERNEL = 0x28`、後続にlittle endianのuint16 ID |
| 命令長 | opcode 1バイト＋ID 2バイト |

CALL_KERNELは`launch`のnと明示引数をスタックへ評価済みの状態で実行する。宣言順にn、各引数を読み、成功時にすべてを消費してNoneを1スロット積む。関数フレームとBPは変更しない。機器APIのCALL_NATIVEは従来のまま使う。

受信時の構造検証ではヘッダー、命令長、非0のID、PC境界などを検査する。登録表とのhash・ID・型列の照合はVM開始時に行い、CALL_KERNELに必要な引数数も登録表から決める。未登録の集合を実行してから不足を検出する方式にはしない。

version 8のイメージとカーネル集合は一組として扱う。登録変更はVM停止中だけ許し、実行中のコードや関数ポインターを置き換えない。version 7にCALL_KERNELを混在させない。version 8を未実装の既存ファームウェアへ送って動作すると説明しない。

現在のコード長上限65536バイト、プログラム全体128KiB、既存の転送・CRC・デバッグPCの意味は維持する。ヘッダー長に依存する配置・長さ計算と、opcode上限・命令走査は実装時に全呼出元を更新する。デバッグのbit7はCALL_KERNELにも適用し、PCは引き続き命令列先頭からの位置とする。

## 7 VMからの同期実行

1. launchの実引数を一度だけ評価し、VMのスタックに保持する。
2. 登録ID・ハッシュ・引数タグを確認し、配列のdtype、1次元、連続配置、入出力の本体共有を確認する。
3. nがint32の非負値であることを確認する。添字の到達範囲、nと配列長の大小、各値の有限性は検査しない。
4. C向けのスカラーと配列ポインター・長さへ変換する。浮動小数点スカラーの有限性検査を行わない専用経路を使う。
5. 公開ラッパーを一度呼び、n要素の計算を最後まで実行する。
6. ブラウザの出力コピーがある場合は完了させ、配列の借用を終え、Noneを返す。
7. tickを終了してホストへ制御を返し、次回にVMの後続命令を実行する。

現在の`BytecodeVM::callNative()`は引数・結果の有限性を検査するため、そのままカーネルの入口として使わない。カーネル専用処理でも、型・スタック範囲・登録情報などの接続検査は行う。既存の機器APIの検査を全体的に無効化しない。

カーネル実行中はGC、VM再入、配列の確保・置換・解放を行わない。VMはlaunchの引数を保持したまま同期的に呼び出す。C側は配列の借用参照を呼出し終了後へ持ち越さない。したがって、初期版で新たな非同期GCルート管理は導入しない。

C計算は分割しない。NativePending、停止フラグ確認、タイムアウト、キャンセル、ネイティブ関数内のステップ実行は追加しない。停止や切断に伴うVM側の後処理は、Cが正常に戻った後にホスト側で行う。計算が戻るまで、ESP32のloopタスクも次の通信・機器処理へ進まない。ハードウェアのwatchdogや実行系のトラップは別の機構であり、この設計で自動的に無効化しない。

デバッガーはlaunch命令の直前と完了後のVM命令を扱う。カーネル本体の行はVMの停止点として登録しない。計算中に停止したと表示せず、VMのinstructionsはC内部の演算数を数えない。

## 8 環境ごとのバッファーと成果物

### 8.1 ESP32

生成Cと登録アダプターを通常のPlatformIOビルドへ組み込む。CはVMの数値配列を同期的に直接借用する。カーネル集合を変更したときは再ビルド・書込みが必要である。同じkernelSetHashを使う通常Python処理だけの変更は、バイトコードの更新で扱う。

本仕様は生成物・ビルド経路の設計であり、ファームウェアのビルド・書込みを自動的に実施する指示ではない。

### 8.2 Colab

Linux向けVMホストを用意し、生成Cを共有ライブラリーへビルドする。VM開始前にマニフェストを照合し、必要な公開関数を読み込んで登録する。配列は同一プロセス内で同期的に借用する。ライブラリーの破棄・置換はVM停止後に行う。本家PythonのNumPy、matplotlib、CPython拡張への接続は追加しない。

### 8.3 ブラウザ

VM用Wasmは開発時にEmscriptenで事前ビルドする。利用時は指定カーネルの生成Cだけをwccでコンパイルし、Binaryenで最適化する。VMと計算用Wasmは同じWorkerに置き、TypeScriptの薄い接続処理を介して、一度の呼出しで計算を完了させる。

初期版はVM用と計算用Wasmのメモリーを分離し、launchごとに配列全体をコピーする。入力だけでなく出力の初期内容もコピーし、完了後に出力配列全体を戻すことで、未書込み要素を保持する。要素ごとのTypeScript呼出し、VM配列の有限性走査、Wasm間のポインターの流用は行わない。

接続用の割当て・コピー処理は計算用Wasmのメモリー上にfloat32の領域を用意し、登録された公開関数へそのメモリー内のアドレスを渡す。必要なメモリー公開・割当て・exportを備えた固定の接続コードだけを生成Cへ添付する。メモリー拡張後のTypedArrayビューは取り直す。wccが出力するWASI依存は必要な範囲を固定ホストで受け、カーネル自体はファイル・ネットワークなどを要求しない。

メモリー共有・ゼロコピーは初期実装の前提にしない。将来追加してもPython側の宣言、launch、kernelSetHashの論理契約は維持し、成果物の接続方式を別のメタデータとして管理する。

## 9 エラーと開始の境界

| 状況 | 扱い |
|---|---|
| 未対応構文、型、書込み先、再帰 | ソース位置付きのコンパイル診断 |
| 未ビルド・登録ID不足 | 開始失敗。NativeUnavailableに対応 |
| ハッシュ・プロファイル・接続ABI不一致 | 開始失敗。AbiMismatchに対応 |
| 引数数・型・配列形式・本体共有の違反 | Cを呼ぶ前にVMエラー。型はType、形状はArrayShape、共有・nはOperandに対応 |
| ブラウザの転送領域などの確保失敗 | Memory。Cを呼ばない |
| Wasmのトラップ | ホストで捕捉できる場合はNativeFailure。出力の正当性を保証しない |
| C実行中の不正な演算・アクセス | 検査・巻戻し・自動再試行を追加しない。環境固有の結果に従う |

計算前の接続エラーは出力を変更しない。実行が始まった後の異常では、出力は未確定であり、全環境でのロールバックは行わない。ネイティブCの異常を必ずVMエラーへ変換できるとは扱わない。

未登録のカーネルを黙ってVM実行へ切り替えない。VMとの速度比較では、同じ数式の通常Python関数を明示的な比較対象として用意する。

プログラムの受信・構造検証完了と、登録照合・VM開始成功と、C計算完了は別の段階である。現在の受信完了やStartの受付を、カーネルの実行完了として扱わない。BLE／Wi-Fiの通常の転送方式は維持し、計算成果物の転送や新しい実行結果パケットは初期版に追加しない。

## 10 実装順と完了条件

| 段階 | 作業 | 完了条件 |
|---|---|---|
| 1 | この仕様と接続形式の文書化 | 宣言・型・生成C・登録・版・エラーの契約が記載されている |
| 2 | ブラウザ用Cコンパイラーの選定 | 完了。[選定記録](browser-c-compiler.md)にwccとBinaryenの固定版・依存・接続APIを記載。比較用コンパイラーは追加しない |
| 3 | Pythonの構文解析・型解析を拡張 | 実装済み。kernel.tsとsemantic.tsがカーネル・launchを静的に解決し、対応外を診断する。C生成・実行は含めない |
| 4 | 数値カーネル用の中間表現とC生成を追加 | 実装済み。型付きIR、共通C、引数型列、kernelSetHash、登録マニフェストを生成する |
| 5 | Colab用ホスト | 同じ生成Cと自作配列を共有ライブラリーで接続できる |
| 6 | ESP32への組込み | 生成CをCとしてビルドし、登録済みカーネルをVMから呼べる |
| 7 | ブラウザ用ツールの導入とVM接続 | 選定した資産とWorker接続を導入し、まとめたコピー、単一呼出し、出力反映まで完了できる |
| 8 | VMとC数値計算の速度計測 | 計算単体、launch全体、プログラム全体、コンパイル時間を区別して示せる |

各ホストへの接続に先立ち、version 8とCALL_KERNELを追加し、VM・受信器・デバッガーの形式認識と専用呼出し経路をそろえる。

コンパイラー間の速度比較は行わない。速度評価は同じ環境のVMとC数値計算の比較とし、転送・呼出し費用と計算そのものを分ける。fast mathによる数値差を記録し、bit単位の一致を合格条件にしない。比較用入力は通常のVMでも正常に計算できる範囲とする。

文書化の段階では実装・ビルド・計測を行わない。以後の各段階でビルド、ブラウザ実行、実機の実行と計測を区別して記録する。
